# Day 4 — Code Review as Communication

**Time: 20 min.**

## Paste into your AI:

```
Day 4 of the Developer EQ Sprint: Code Review as Communication.

Code review comments are seen by more people than your
standup voice. They're permanent. They show up in promotion
packets — yours and other people's.

Two failure modes:
- Too harsh: "This is wrong" → reader hears "you are dumb"
- Too soft: "Have we considered maybe possibly..." → no
  actionable feedback, ship the bug, you get blamed

Win = direct + warm. Pick the change. Explain why in one
sentence. Move on.

Help me practice:

1. Ask me to paste my last 5 code review comments (or the
   last comment I almost sent). If I have GitHub CLI
   installed, suggest: gh pr list --author=@me --state=all
   --limit=10
2. From those, help me pick the one I'd be MOST embarrassed
   to have read aloud at all-hands.
3. Help me rewrite it three ways:
   - BLUNT: direct, no fluff, here's the change
   - WARM: same change + 1 sentence why + 1 sentence
     acknowledging author's intent (max 4 sentences total)
   - TEACHING: for a junior reviewer where I want them
     to grow
4. Ask me which version fits my team's actual culture.
5. Save the version I'll default to going forward.

Tone: peer-to-peer. If my original comment is condescending,
say so. If it's too vague, say so.
```

## What "done" looks like

- All three rewrites completed (don't skip the blunt one)
- The warm version is < 4 sentences
- You know which version your team's culture rewards
